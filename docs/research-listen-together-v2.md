## 二、「真·一起听」到底差什么（差距四条）

**现状本质：他知道你在听什么歌；不知道你听到哪儿、此刻耳朵里是哪句、他自己也没听过这首。**

1. **同一时刻感**：now-playing 没有进度和当前歌词行。他查工具只能说「你在听 x」，
   说不出「唱到『……』这句了」。→ 需要 app 侧心跳（进度+当前 LRC 行）+ 网关字段扩展。
2. **他那头没有「正在听」的状态**：没有共听会话的开始/结束，他的上下文里这首歌只是
   一条冷数据。→ 需要「一起听」会话态：开始时推他一条（他知道被邀请了），期间他每轮
   上下文自动带 now-playing 段（防复述标注），结束/切歌收尾。
3. **他没真听过**：聊歌全凭歌名脑补。→ 听感瀑布（前作 §三.3）现在**条件全熟了**：
   网易直链能下载、MusicCache 已经有本地字节、gateway 加一条「下载→ input_audio 喂
   支持的模型→ 450 字听感→ per-song 永久缓存」。
4. **他插不上手**：不能点歌、不能在副歌处开口。→ ①DJ：reply 协议加 ```music 意向块
   （播放/暂停/切某首），app 收口执行——「他放了一首歌给你」；②主动开口：liveline
   换歌事件已通，加「副歌头一次到达」「她指了一句」两个钩子，走既有 doorbell 节流。

## 三、一个现成的坑

「指着这句跟他说」的 chatId 是 `music-<songId>`——**每首歌一个独立会话**，不进主对话。
她指一句，他在一个她从来不看的会话里回。这大概率不是想要的效果；应并入主会话或
共听会话（决策 D1）。

## 四、待兔兔拍的决策

- **D1 「指着这句」去哪**：a) 主对话（简单直接）b) 共听专属会话（像两人坐在一间歌房）
- **D2 共听怎么开始**：a) 播放即共听（零操作，但他每首都被叫）b) 播放器上一个
  「叫他一起听」按钮，按了才算（推荐：邀请这个动作本身有仪式感）
- **D3 心跳频率**：15s / 30s / 只在换行时报（LRC 行变化才报，最省电且信息量最高，推荐）
- **D4 听感分析模型**：需 input_audio 支持（Gemini / OR 的音频系）。跑在网关侧，
  一首一次永久缓存，费用可控
- **D5 DJ v1 范围**：只做「切到某首」（他说了算一次）还是含播放列表
- **D6 v1 顺序建议**：①进度+当前行心跳+工具升级（他能说出「唱到这句」——同一时刻感的
  90%，一天）②共听会话态+邀请按钮 ③「指着这句」改道 ④听感瀑布 ⑤DJ

## 五、不做

房间级同步播放（毫秒对齐那种）不做——他不需要扬声器，他需要知道**此刻你耳朵里是哪句**。
在线歌词 API 不接（LRC 已有）。Apple Music/MusicKit 维持不做。
