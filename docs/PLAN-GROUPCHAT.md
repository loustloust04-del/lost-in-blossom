# 群聊重做方案（API + CC 丝滑同群）

> 目标：不同模型（API 各家 / CC）在一个群里像真人一样自然地互相接话。
> 现状定位 + 分期改造。执行节奏：一次一件事 → 编译验绿 → 出包 → 验收。

## 一、现状架构（群聊 V5）

- `runGroupRound`（ConversationViewModel+Group.swift）：用户发言入树 → 循环「选人 → 说话」最多 3 轮。
- `GroupChatScheduler.selectNextSpeaker`：**单次 LLM 调用当"主持人"**，从名单里挑下一个说话的人（或"无"）。
- `groupSpeak`：站在被选中角色的视角重建 messages（镜像：自己=assistant、别人=`[名字]: …`user），调 `providerRouter.sendStreaming` 出一条回复。
- 每条 AI 回复后扫 `@名字`，命中就让下一轮选中被 @ 的人。

## 二、三个 bug 的根因（都已定位）

### Bug 1 · 概率性空回
`groupSpeak` 无论模型返回什么，都会先插一个 assistant 节点、再把 `fullText` 塞进去。
而 system prompt 明写「如果觉得不需要回复，可以保持沉默」——模型真的返回空/纯空白时，
就留下一个**空气泡**。选人环节 `selectNextSpeaker` 的 @ 预判又极松（`content.contains(p.name)`
命中任意子串），会选出一个其实没话可说的人 → 空回。
**修法**：① 空/纯空白回复不插节点（或插了就删）；② 选人预判从"含名字"收紧到"真正 @ 或明确点名"。

### Bug 2 · 聊天页没做群聊适配
气泡已有发言者名 + 按 senderId 稳定取色（这部分在），但缺：
- 输入框 `@` 自动补全（打 @ 弹成员列表）
- 成员栏 / 头像（谁在群里、谁在打字）
- 定向说话（想点某个角色回）
- 群聊语义的分隔（谁对谁说）

### Bug 3 · CC 加群成功但消息发不过去 ★根因最明确
单聊在 `prepareRouterPayload` 里给 CC 车道组装了路由头：
`X-MP-ChatId`（对话id）、`X-MP-MessageId`、`X-MP-User`、`X-MP-Context`（最近对话）。
而群聊的 `groupSpeak` 调 `sendStreaming` 时**一个 header 都没传**。后果：
1. CC 拿不到 `X-MP-ChatId` → CCBridgeProvider 用随机 UUID 兜底 → 回复路由不稳。
2. CC 天生**丢弃 systemPrompt**（只取最后一条 user 文字），群聊规则/成员名单/角色设定
   全在 systemPrompt 里 → CC 根本不知道自己在群里、是谁、有哪些人。
3. 多个 CC 角色没有各自的 `X-MP-CCSession` → 全挤默认 tmux 会话，互相打架。
**修法**：群聊给 CC 组装完整路由头；把群聊规则+角色设定**拼进 CC 的消息正文**（因为 CC 不读 system）；
每个 CC 角色分配独立 session 名（如 `mp-group-<convId>-<participantId>`）。

## 三、借鉴的多角色群聊经验（挑适配双车道的）

| 经验 | 采纳 | Bunny 落地方式 |
|---|---|---|
| **发言门控**（每个 bot 独立 YES/NO 判断要不要回） | ✅ 核心 | 用**最便宜的 API 模型**统一跑门控（即便该角色本体是 CC，门控也走廉价 API，不用 CC 做 YES/NO——CC 慢且贵）。取代现在的单主持人选人 |
| **表达约束 > 性格标签**（规定句式/标点/emoji/字数） | ✅ | 建群/编辑角色时提供"表达风格"模板字段，注入 system；差异度足够才有涌现 |
| **顺序回复 + 上下文接力**（先回的进后回的 context） | ✅ 已部分具备 | 每轮 `groupHistoryItems()` 已带最新；加 0.5–2s 随机延迟做打字感 |
| **模型路由**（贵模型只用在最终回复；门控/摘要用便宜的） | ✅ | 门控=便宜模型；回复=角色本体模型（API/CC）；群摘要=中等模型 |
| **群聊记忆带发言人归属** | 🟡 P4 | 群摘要标注谁说了什么，检索不丢主语 |
| Life Tick / 主动消息 / 内心独白 | ⏸️ 归 AUTONOMY | 已在 ROADMAP P3-12，群聊先不掺 |

## 四、分期方案

### P0 · 修三个 bug（先让它能用，改动小）
- Bug1：空回不落气泡 + 选人 @ 预判收紧。
- Bug3：`groupSpeak` 给 CC 车道补 `prepareRouterPayload` 同款路由头；CC 消息正文前置拼入
  "群聊规则 + 你是谁 + 成员名单 + 你的角色设定"；每个 CC 角色独立 session 名。
- Bug2 先做最小：气泡已有名字+颜色，补一个顶部成员栏（谁在群、谁在说）。

### P1 · 发言门控重构（体验核心）
- 用便宜 API 模型对每个（非刚发言的）角色跑 YES/NO 门控：有人@我 / 话题相关 / 别人没充分回应 → YES；
  刚回过 / 话题跟我无关 / 已被充分回应 → NO。输入=最近若干条群消息 + 角色简述。
- 一轮里所有 YES 的角色按顺序发言（先回的进后回的 context），每人加随机延迟。
- 保留 @ 强制命中（被 @ 必回）。
- 干掉"单主持人选一个"——改成"人人独立决定"，节奏更自然（通常 1–2 个回，偶尔仨）。

### P2 · 聊天页群聊适配
- 输入框 `@` 自动补全弹成员。
- 顶部成员栏（头像/颜色/在线态），"XX 正在输入…"。
- 长按消息可"让某角色回应这条"。

### P3 · 表达约束 + 涌现
- 建群/角色编辑加"表达风格"引导（句式、标点、emoji、字数、是否省略主语），
  而非抽象性格词；模板可选。
- 放宽单轮回复上限与上下文窗口，观察涌现（互相拆台/临时联盟）。

### P4 · 群聊记忆
- 群摘要独立于单聊，带发言人归属；记忆检索标来源（私聊/群聊）。

## 五、先做哪一步
建议 **P0 先修 bug**（尤其 Bug3 让 CC 真正能在群里说话），出一版验收；
体验层的门控重构（P1）确认 P0 稳了再上。UI（P2）大改留真机验收。
