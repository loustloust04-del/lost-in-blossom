# Localization Readiness Review

Date: 2026-07-14
Scope: MemoryPalace iOS app (`MemoryPalace/`), audited on VPS working copy.

## Verdict

**Not localization-ready.** The app is single-language (Simplified Chinese), with zero localization infrastructure in place. All user-facing text is hardcoded Chinese string literals. Internationalizing would be a large, codebase-wide effort.

## Findings

### 1. Localization resources: none

- No `.strings`, `.stringsdict`, or `.xcstrings` (String Catalog) files anywhere in the repo.
- No `.lproj` directories.
- Project is generated by XcodeGen (`project.yml`); no `knownRegions`/localization config declared there either.

### 2. Localization APIs: never used

| API | Occurrences |
|---|---|
| `String(localized:)` | 0 |
| `NSLocalizedString` | 0 |
| `LocalizedStringKey` (explicit) | 0 |

SwiftUI `Text("...")` does treat literals as `LocalizedStringKey` implicitly, but with no string catalog/table present, every key falls through to the literal itself. Interpolated and programmatic strings (`String` properties, model `displayName`s, etc.) bypass localization entirely.

### 3. Hardcoded Chinese string literals

Lines containing string literals with CJK characters (`grep -rnP '"[^"]*[\x{4e00}-\x{9fff}]' --include="*.swift"`):

| Location | Count |
|---|---|
| `MemoryPalace/Views/` (105 files) | **1,865** |
| `MemoryPalace/Services/` | 468 |
| `MemoryPalace/Models/` | 104 |
| `MemoryPalace/ViewModels/` | 81 |
| `MemoryPalace/Utils/` | 35 |
| **Total (`MemoryPalace/`, 259 Swift files)** | **2,597** |

Note: counts include comments as well as user-facing literals, but spot checks confirm the bulk in `Views/` are real UI strings (labels, placeholders, empty states, button titles, error messages).

Top offender files:

- `Views/WorldBookPanelView.swift` — 91
- `Views/PersonaSettingsTab.swift` — 89
- `Views/GatewayConsoleView.swift` — 89
- `Views/APISettingsTab.swift` — 71
- `Views/SidebarView.swift` — 66
- `Views/AppearanceSettingsTab.swift` — 64
- `Views/CardFlowView.swift` — 57
- `Views/ImportView.swift` — 55

Sample (`Views/SidebarView.swift`):

```swift
case .all: return "全部"
case .favorites: return "收藏"
case .trash: return "回收站"
TextField("搜索对话...", text: $searchText)
@AppStorage("userName") private var userName = "你"
```

The last line is notable: Chinese is used as a *persisted default value*, which is worse than a display literal — it ends up in stored data.

### 4. Info.plist / project configuration

- `MemoryPalace/Info-iOS.plist` sets `CFBundleDevelopmentRegion = $(DEVELOPMENT_LANGUAGE)` (default `en`), which mismatches the actual app language (zh-Hans).
- No `CFBundleLocalizations` key; the app declares no supported languages.
- `project.yml` has no localization settings.

### 5. Locale handling in code

Mixed and hardcoded:

- `Locale(identifier: "zh_CN")` hardcoded in `Services/Search/WebSearchToolService.swift:52`, `Views/CalendarPanelView.swift:282,289`, `ViewModels/ConversationViewModel+Chat.swift:87` — date formatting is pinned to Chinese regardless of user locale.
- `en_US_POSIX` used correctly for machine-readable timestamps (`Utils/TimestampFormatter.swift`, `Services/RecallTool.swift`, etc.) — these are fine and should stay.

### 6. Non-Swift UI surfaces

- `Resources/message-renderer.html` (WKWebView message renderer) contains 29 lines with Chinese text — a second localization surface outside any Apple localization mechanism.
- Bundled CJK fonts (`SourceHanSerifSC-Regular.otf`, `LXGWWenKai-Regular.ttf`) are wired into the typography system; a non-CJK locale would need font fallback review.

## Readiness assessment

| Dimension | Status |
|---|---|
| String externalization | ❌ 0% — ~2,600 hardcoded literals |
| Localization APIs | ❌ Not used at all |
| String catalog / .strings infra | ❌ Absent |
| Declared supported languages | ❌ None (dev region mismatched) |
| Locale-aware formatting | ⚠️ Partially; zh_CN pinned in 4+ sites |
| Web/HTML surfaces | ❌ Chinese hardcoded in renderer HTML |

## Recommendations (if/when localization is wanted)

1. **Decide the target.** If the app remains personal/single-user zh-Hans, the pragmatic fix is minimal: set `CFBundleDevelopmentRegion` to `zh-Hans` in `Info-iOS.plist` so the declared language matches reality, and stop there.
2. For real i18n:
   - Add a String Catalog (`Localizable.xcstrings`) via XcodeGen and enable `localizedStrings` extraction; Xcode 16 auto-extracts SwiftUI `Text` literals.
   - Migrate programmatic strings (Services/Models/ViewModels, ~650 lines) to `String(localized:)`.
   - Replace `Locale(identifier: "zh_CN")` date formatters with `Locale.current` or template-based formatting.
   - Extract strings from `message-renderer.html` into an injected dictionary.
   - Fix the `userName = "你"` persisted default and any other Chinese defaults written to storage.
3. Prioritize `Views/` top offenders above; the eight files listed cover ~30% of view-layer strings.

## Raw check commands

```
find . -name "*.strings" -o -name "*.stringsdict" -o -name "*.xcstrings" -o -name "*.lproj"   # -> empty

grep -rn 'NSLocalizedString' --include="*.swift" . | wc -l                                     # -> 0
```
